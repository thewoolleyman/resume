## Decision and Rationale

All four findings in codex-gpt-5-critique are real, load-bearing gaps; accept them with resolutions that preserve the settled gate-enforced anchor-test TDD model, the top-of-pyramid E2E discipline, and the design-record's guardrails-first stance. The decision is 'modify' because the guardrail-bootstrap resolution (P3) deliberately follows the maintainer's confirmed additive-ordering direction rather than inventing a spec-level bootstrap-mode flag or a stricter self-hosting rule. Design-record note (per the intent-preservation gate): plan/adversarial-spec-hardening/research/findings.md establishes 'the first real code is the harness' but does not pin the bootstrap-boundary mechanics; the maintainer resolved that open edge in-session by rejecting the chicken-and-egg framing and directing that correct additive ordering (owned by the guardrail-implementation plan) makes the build additive rather than circular. This revision fills that edge with the maintainer's confirmed decision; it does not depart from any cited ratified record.

## Modifications

P1 (Scenario coverage forces Playwright onto non-browser phase-1 scenarios) - ACCEPT, resolved in §"Top-of-pyramid discipline": every load-bearing scenario is now classified browser-observable (requires >=1 Playwright mapping) or non-browser-exercisable (requires >=1 mapping to a named non-Playwright top-level category - a Vitest unit/integration test, a fast-check property/fuzz test, or a build/prerender check - plus a one-line misleading-Playwright rationale). The classification is explicitly generalized to the EXISTING phase-1 scenario set, naming Search-projection-without-a-DOM, malformed-data build failure under the build-time load, and pinned-inventory round-tripping as non-browser-exercisable. check:scenarios must verify class-appropriate resolvable mappings and reject class-dodging (a browser-observable scenario mis-declared non-browser to avoid Playwright). Kept in non-functional-requirements.md + the committed scenario-coverage mapping so scenarios.md prose is not churned (functional-file hardening is the next phase); the 'Scenario coverage gate protects acceptance behavior' contributor scenario is updated to match. No scenarios.md edit.

P2 (Final Red->Green trailer shape still ambiguous after TDD-Intent) - ACCEPT, resolved by pinning the trailer grammar in §"Mechanically enforced Red -> Green commit protocol": the transient pre-amend Red commit carries TDD-Intent: Red with only TDD-Red-*; the durable amended Red->Green commit flips to a single TDD-Intent: Green alongside the full TDD-Red-* and TDD-Green-* sets (the persisted Red trailers are required evidence, not a second intent); a Suite-Green commit carries TDD-Intent: Suite-Green with only TDD-Suite-Green-*. 'Conflicting TDD-Intent' is defined as more than one distinct TDD-Intent value on a single commit. The origin/master..HEAD range validation is tied to the grammar (pair shape => TDD-Intent: Green, Suite-Green shape => TDD-Intent: Suite-Green) so a final amended commit has exactly one valid interpretation. The 'TDD Red -> Green protocol is mechanically enforced' scenario is updated.

P3 (Guardrail bootstrap boundary undefined) - ACCEPT, resolved per the maintainer's confirmed additive-ordering direction: added §"Guardrail provisioning boundary" defining the 'first non-trivial implementation merge' as the first change landing first-party product source under src/** on master (PR merge or sanctioned direct-owner commit), excluding harness/tooling, spec, docs, and governed-data commits; and requiring the harness to be provisioned ADDITIVELY - each gate enforced from the commit that introduces its own artifact onward, every required gate present/operational/green as a precondition of that first src/** merge, with no bootstrap-mode window and no self-bootstrapping gate. Per the maintainer, the spec adds NO bootstrap-mode flag (rejected option B) and NO strict self-hosting-from-commit-1 rule (rejected option C); additive ordering owned by the guardrail-implementation plan keeps the build additive rather than circular. A new 'Guardrail gates are provisioned additively before the first product-source merge' scenario asserts the precondition.

P4 (Coverage thresholds have no enforceable floor) - ACCEPT, resolved in §"Test coverage expectations": committed thresholds must clear non-trivial floors (first-party core >= 90% line, 90% function, 85% branch; framework glue >= 60% line, or a documented stricter equivalent); bun run check must fail when any threshold is below its floor or when core is not strictly higher than glue on every dimension; per-module exemptions require a rationale and revisit condition and must never silently drop a core module below the core floor. Exact percentages are flagged as a low-level realization tunable via a future proposed change (design-record exit criterion), but the floor must stay non-trivial. A new 'Coverage thresholds cannot drop below the committed floor' scenario asserts the gate.
