## Proposal: Coverage is 100% line and branch for first-party product source, non-negotiable

### Target specification files

- SPECIFICATION/non-functional-requirements.md

### Summary

Replace the tiered core/glue coverage-floor apparatus in §"Test coverage expectations" with one non-negotiable rule: first-party product source under src/** MUST have 100% line and 100% branch coverage. Remove the core-vs-glue tiers, the framework-glue line-only floor, the "strictly higher on every dimension" relative rule, the per-module exemptions, and the tunable-percentages language. Function coverage is subsumed by 100% line coverage. Generated artifacts and repository harness/tooling stay outside the first-party product-source set (as already defined for the TDD pairing gate) and are not counted. Update the dependent scenario 'Coverage thresholds cannot drop below the committed floor' to 'below 100%'.

### Motivation

The tiered floors (core 90/90/85, glue 60 line, core strictly > glue on every dimension, exact percentages tunable) are an over-complicated apparatus that produced repeated critique churn — most recently a finding that the 'strictly higher on every dimension' comparison is undefined on the function and branch dimensions where glue carries no committed floor. The maintainer has ratified a simpler, stricter rule: nothing in well-factored, loosely coupled, highly cohesive first-party product logic is un-coverable at the unit level — dependency injection and module mocking can inject whatever a branch needs — so 100% line and branch coverage is always achievable and is non-negotiable. Flat 100% is strictly less ambiguous than tiers and removes the entire coverage critique surface. This reverses the Settled v017 coverage-floor decision with maintainer sign-off.

### Proposed Changes

In §"Test coverage expectations", replace the whole tiered-floor paragraph with: 'Before the first non-trivial implementation merge, the repository MUST document explicit line and branch coverage thresholds and `bun run check` MUST enforce them. Coverage of first-party product source under `src/**` (the product-source set defined in §"Mechanically enforced Red -> Green commit protocol") MUST be 100% line and 100% branch — non-negotiable. Nothing in first-party product logic is un-coverable at the unit level: well-factored, loosely coupled, and highly cohesive code, with dependency injection and module mocking used to inject whatever inputs a branch requires, can always reach 100% line and branch coverage, so there is no lower tier, no framework-glue exemption, and no per-module coverage carve-out. `bun run check` MUST fail when the committed thresholds are set below 100% line or 100% branch for first-party product source, and MUST fail when any first-party `src/**` source file is below 100% line or 100% branch coverage. Function coverage is subsumed by 100% line coverage. Generated SvelteKit artifacts, generated types, built assets, and repository harness/tooling are outside the first-party product-source set and are not counted toward this threshold; harness/tooling is covered by its own tests or checks as required by §"Mechanically enforced Red -> Green commit protocol".' Rewrite the 'Coverage thresholds cannot drop below the committed floor' scenario as 'Coverage thresholds cannot drop below 100%': Given the committed coverage thresholds set first-party product source below 100% line or 100% branch, or a first-party `src/**` source file is below 100% line or branch coverage / When the aggregate check command runs / Then the coverage gate fails before merge.

## Proposal: TDD gate is content-triggered; remove the invented TDD-Intent discriminator

### Target specification files

- SPECIFICATION/non-functional-requirements.md

### Summary

Rewrite §"Mechanically enforced Red -> Green commit protocol" so the TDD leg is selected by CONTENT — the staged buckets (first-party product source vs test files) plus the repository's HEAD trailer state — rather than by an explicit TDD-Intent trailer. Remove the invented `TDD-Intent` marker, the 'missing/unknown/conflicting TDD-Intent MUST reject / exactly one deterministic leg' language, and the 'test-support-genesis' zero-test allowance. Keep the Red/Green/Suite-Green legs, the singular anchor-test checksum, the `TDD-Red-*`/`TDD-Green-*`/`TDD-Suite-Green-*` trailer sets, the per-commit commit-msg hook, the `origin/master..HEAD` range validation, and the full-suite-runs-in-the-hook Suite-Green behavior. State the model as our own standalone rules — no reference to any external project. Update the 'TDD Red -> Green protocol is mechanically enforced' scenario to the content-triggered shape.

### Motivation

The spec had diverged from a proven mechanism by inventing an explicit `TDD-Intent` discriminator and a 'leg selection is NOT the subject prefix' rule (Settled v016), then polishing that invented variant across multiple versions. That is the source of the repeated TDD critique churn: an invented variant has no reference behavior, so every critique pass finds a new under-specified edge (when the full suite runs, whether every commit needs a marker, etc.) and every revise pass patches it, opening the next. The maintainer has ratified capturing the proven content-triggered model instead. Doing so resolves both of the prior critique's TDD findings directly: the full-suite-in-the-commit-hook is intended (not a contradiction with §"Hooks"), and commits touching neither product source nor tests pass immediately with no leg (so there is no every-commit marker requirement). This reverses Settled v016 with maintainer sign-off, and keeps the specification standalone.

### Proposed Changes

Rewrite the subsection so TDD is a CONTENT-TRIGGERED gate. Standalone rules to encode: (1) The gate is a standalone TypeScript/Bun commit-msg hook plus an `origin/master..HEAD` range validation; leg selection is determined by what is staged and the repository HEAD state, NOT by an intent marker and NOT by the commit subject prefix. The subject prefix MUST NOT reject a commit for containing product source (a behavior-changing chore follows Red -> Green exactly like a feature); the prefix's only load-bearing role is that a `feat:`/`fix:` subject staging a passing test alone is rejected (a declared behavior change must fail first). (2) Classification excludes staged deletions and buckets staged files into first-party product source under `src/**` and test files (`*.test.ts`/`*.spec.ts`/`e2e/**`); files in neither bucket — configuration, documentation, specifications, governed data, generated artifacts, lockfiles, harness/tooling — do not participate and cannot trigger a leg. (3) commit-msg decision tree: [a] nothing in either bucket → pass immediately for any subject (documentation, configuration, spec, governed-data, generated-artifact, and empty commits included), no trailers required; [b] only test files staged and the staged anchor test FAILS → Red leg (any subject): exactly one anchor test file may be staged (the anchor checksum is singular; more than one test file rejects); the hook runs the anchor (Vitest or Playwright) and it MUST fail meaningfully (assertion, not import/collection error); records `TDD-Red-Test`, `TDD-Red-Failure-Reason`, `TDD-Red-Test-File-Checksum` (sha256 of anchor bytes), `TDD-Red-Output-Checksum`, `TDD-Red-Captured-At`; a passing anchor at Red rejects; [c] only test files staged and they PASS → a `feat:`/`fix:` subject rejects (declared behavior change needs a failing test first); any other subject is a passing test-only cleanup and takes the Suite-Green leg; [d] product source staged and HEAD carries `TDD-Red-*` WITHOUT `TDD-Green-*` (a genuine amend-in-progress) → Green leg (subject-agnostic): recompute the anchor's sha256 and reject unless byte-identical to `TDD-Red-Test-File-Checksum` (changing the anchor requires a new Red), re-run the anchor and require pass, record `TDD-Green-Verified-At` and `TDD-Green-Parent-Reflog`; [e] product source staged without a Red-awaiting-Green HEAD (refactor / behavior-preserving chore / fresh commit atop completed history, any subject) → Suite-Green leg: the FULL suite MUST pass against the staged tree (clean exit only; a zero-test run rejects), record `TDD-Suite-Green-Scope` (full-suite), `TDD-Suite-Green-Output-Checksum`, `TDD-Suite-Green-Captured-At`. (4) The final durable Red -> Green commit carries the anchor test, the implementation, any supporting/updated test files, and both trailer sets; only the one designated anchor is checksummed. (5) The per-commit commit-msg hook fires before each commit lands (working for both direct-owner commits to `master` and PR branches); it is complemented by a branch-range validation that `bun run check` and CI run over `origin/master..HEAD`: every non-merge commit touching first-party product source MUST carry EITHER the `TDD-Red-*`/`TDD-Green-*` pair shape OR the `TDD-Suite-Green-*` shape, regardless of subject, so a rebase/squash/history-rewrite cannot launder a commit; a commit that only deletes product source is not flagged; merge commits are skipped; an unresolvable range base (shallow CI checkout) MUST fail actionably rather than silently pass. (6) The repository MUST provide a `tdd-commit` helper mechanizing stage-anchor-alone -> commit -> stage-impl -> amend for Red -> Green, plus a Suite-Green mode. (7) Keep the existing first-party product-source definition paragraph unchanged. Remove every mention of `TDD-Intent`, the 'exactly one deterministic leg / missing marker MUST reject' language, and the 'test-support-genesis' zero-test allowance. Also update the earlier intro paragraph of the subsection to describe the content-triggered trigger instead of the `TDD-Intent`-selected trigger. Update the 'TDD Red -> Green protocol is mechanically enforced' scenario: Given a commit changes first-party product source without a valid `TDD-Red-*`/`TDD-Green-*` pair or valid `TDD-Suite-Green-*` evidence, or amends a Green leg after the anchor test file's bytes changed / When the commit-msg hook fires or the `origin/master..HEAD` range validation runs / Then the commit is rejected — or the branch range fails — unless the staged tree and HEAD state select one leg by content and the commit carries the pair shape or the Suite-Green shape, with the anchor checksum matching the recorded Red digest even when the commit also stages other implementation and test files.
